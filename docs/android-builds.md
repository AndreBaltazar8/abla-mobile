# Android application builds

Android package metadata is defined in an Abla build program, alongside the
request that compiles the application object. No manifest, theme, resource, or
Kotlin application source needs to be generated by Gradle.

## One build call

```abla
import "path/to/abla-mobile/src/android_build.ab"

val android = #mobileBuildAndroid(MobileAndroidConfiguration(
    "my-app-debug",
    "mobile/app.ab",
    "android-app",
    "debug",
    mobileAndroidApplication(
        "com.example.myapp",
        "My Abla App",
        1,
        "0.1.0"
    ),
    mobileAndroidBranding("#10131A", "@drawable/splash_icon"),
    [mobileAndroidInternetPermission()],
    [mobileAndroidDeepLink(
        "https", "example.com", "/open", true
    )],
    true,
    false
))

fun main: int = if (android) 0 else 1
```

The build package must authorize `filesystem.write` in its nearest
`abla.toml`:

```toml
compileCapabilities = ["filesystem.write"]
```

The call transactionally writes these ignored build inputs under
`android-app/build/abla-mobile/debug/`:

- the ARM64 Abla application object and ABI sidecars;
- `application.properties` for Gradle package/version/SDK configuration;
- a generated `AndroidManifest.xml`; and
- generated title, splash color, and API-31 splash theme resources.

An invalid configuration or failed child compilation rolls the complete set
back. Existing app drawables remain ordinary Android resources. Branding
fields such as `@drawable/splash_icon`, `@mipmap/app_icon`, and a custom theme
parent refer to those resources; an empty icon lets Android use its default.

`mobileAndroidApplication` supplies the preview SDK and safety defaults. Use
the full `MobileAndroidApplication` constructor to control SDK levels,
backup/RTL behavior, or cleartext traffic. Use the full
`MobileAndroidBranding` constructor for launcher icons and the post-launch
theme parent.

The app module reads the selected generated directory with
`-PablaMobileConfiguration=debug`. Its stable Gradle and CMake adapters are
application packaging boilerplate, not generated Kotlin. See the
`examples/showcase/android-app` module for the complete consumer.

## Configurations and variants

`variant` is a safe directory key containing letters, numbers, `_`, or `-`.
Several package configurations can be emitted in one graph without defining
the Android target twice:

```abla
val variants = #mobileBuildAndroidConfigurations([
    debugConfiguration,
    releaseConfiguration
])
```

Every configuration needs a unique build `name` and variant. Gradle selects
the matching generated package inputs, for example:

```sh
android-gradle :android-app:assembleRelease \
  -PablaMobileConfiguration=release
```

This allows application ID suffixes, labels, versions, capabilities, links,
branding, and compiler optimization/cache policy to differ without application
Kotlin. Signing and Android build-type policy still belong to Gradle and must
not be placed in a source-controlled secret.

## Permissions and intents

These Android concepts have different lifetimes:

- `permissions` are install-time manifest declarations. Internet access is
  `mobileAndroidInternetPermission()`; the HTTP work and response state still
  belong to Abla. Camera and notification helpers only declare capability—any
  required runtime permission request still needs the future request/completion
  API.
- `intentFilters` describe incoming Android intents that may launch the shared
  activity. `mobileAndroidDeepLink` creates the standard `VIEW`, `DEFAULT`, and
  `BROWSABLE` filter. The full `MobileAndroidIntentFilter` also supports custom
  actions, categories, URI parts, and MIME types.
- outgoing intents are runtime effects. `mobileOpenUrl` already asks Android to
  open an allowlisted `http` or `https` URI through a copied payload. Future
  share/email/dial/map effects follow that same boundary.
- incoming URI/action delivery into the running Abla event loop is not yet
  implemented. Current filters route and launch the application, but the app
  cannot branch on their payload until a copied launch-event API is added.

No intent boundary stores an Abla closure or state handle. Result-bearing
operations will use copied request IDs and copied completion events.

## Splash screens

The generated base theme uses the configured splash background as its legacy
window background. On Android 12 and later, a `values-v31` override sets the
system splash background and, when supplied, the animated-icon resource. The
splash exists before `mobileRun` starts, so its configuration is package
metadata rather than reactive `$mobile` state.

The implementation uses the platform splash window and does not create a
dedicated splash activity. This avoids a second splash and generates no
application Kotlin.
